# NameVecs — Text Embedding Vectors in PostgreSQL via pgvector

## Overview

`pgNameVecs` stores 1024‑dimensional normalized embedding vectors for items
in a PostgreSQL table using the `vector` extension (via the `pgvector`
Python package).  Vectors are generated by an OpenAI‑compatible embedding
API, normalized to unit length, and searched via the pgvector `<=>`
cosine‑distance operator.

The vector table is named `{item_table}_name_vecs` with:

| Column | Type | Description |
|---|---|---|
| `oparl_key` | `VARCHAR(500)` PK | References the item's `oparlKey` |
| `embedding` | `vector(1024)` | 1024‑dim embedding vector |

The **item table is never modified**.

## Quick start

```python
import os
from sqlalchemy import create_engine
from name_vecs import NameVecs

engine = create_engine(os.environ["DATABASE_URL"], future=True)

nv = NameVecs(
    engine,
    item_table="items",
    embedding_url=os.environ.get("EMBEDDING_URL", "http://localhost:8085/v1"),
    embedding_model=os.environ.get("EMBEDDING_MODEL", "bge-m3-Q4_K_M"),
    api_key=os.environ.get("EMBEDDING_API_KEY", ""),
)

# Store vectors by embedding text
nv.upsert("oparl:123", "Python programming language")
nv.upsert("oparl:456", "Java virtual machine")

# Search by cosine similarity
results = nv.find_similar("python coding", k=5, cutoff=0.4)
for key, sim in results:
    print(f"{key}: {sim:.4f}")

# Remove a vector
nv.remove("oparl:456")
```

## Requirements

- PostgreSQL with the `vector` extension:
  ```sql
  CREATE EXTENSION IF NOT EXISTS vector;
  ```
- Python packages: `sqlalchemy>=1.4,<2`, `psycopg2-binary`, `numpy`,
  `requests`, `pgvector`

## Public API

### `NameVecs(engine, item_table, embedding_url, embedding_model, api_key)`

| Parameter | Type | Description |
|---|---|---|
| `engine` | `sqlalchemy.engine.Engine` | PostgreSQL engine (schema must exist) |
| `item_table` | `str` | Existing table name with an `oparlKey` column |
| `embedding_url` | `str` | OpenAI‑compatible API base URL |
| `embedding_model` | `str` | Model name (e.g. `bge-m3-Q4_K_M`) |
| `api_key` | `str` | API key (blank allowed for local endpoints) |

Raises `ValueError` if the item table does not exist.

---

### `upsert(oparl_key, text)`

Insert or update the vector for `oparl_key` by embedding `text`.

| Parameter | Type | Description |
|---|---|---|
| `oparl_key` | `str` | The item's `oparlKey` |
| `text` | `str` | Source text to embed |

---

### `remove(oparl_key)`

Remove the vector entry for `oparl_key`.  No error if missing.

---

### `find_similar(text, k=5, cutoff=0.4)`

| Parameter | Type | Default | Description |
|---|---|---|---|
| `text` | `str` | — | Query text to embed |
| `k` | `int` | `5` | Max results |
| `cutoff` | `float` | `0.4` | Min cosine similarity (strict `>`) |

Returns `list[tuple[str, float]]` — `(oparl_key, similarity)` pairs,
sorted by similarity descending.  Empty list if no vectors or no results
pass the cutoff.

---

## Embedding API

The `_embed` method sends a POST to `{embedding_url}/embeddings` with an
OpenAI‑compatible JSON body:

```json
{
  "model": "bge-m3-Q4_K_M",
  "input": "...",
  "dimensions": 1024
}
```

The raw response vector is normalized to unit length (L2 norm = 1) so that
cosine similarity equals the dot product.

---

## Similarity search

Uses the pgvector `<=>` (cosine distance) operator directly in SQL.
Cosine distance values are in [0, 2]; cosine similarity = 1 − distance.

The database query computes:
- **WHERE**: `cosine_distance < 1 − cutoff`  
- **ORDER BY**: cosine_distance ascending  
- **LIMIT**: `k`

## Design notes

### Why pgvector instead of raw FLOAT columns?

- Production‑ready: pgvector is the standard PostgreSQL extension for
  vector similarity search.  Applications that outgrow brute‑force can
  add an IVFFlat or HNSW index without changing client code.
- The `<=>` operator is far more ergonomic than fetching all rows and
  computing cosine similarity in Python.  It also opens the door to
  approximate nearest‑neighbour (ANN) indexes for large datasets.
- Storage: one `vector(1024)` column instead of 1024 separate `FLOAT`
  columns — more compact and indexable.

### Why brute‑force search?

The current implementation issues a plain `SELECT` with `<=>` and
`ORDER BY` / `LIMIT` — no index required.  For small to medium datasets
this is perfectly adequate and keeps the code simple.  Adding a pgvector
index is a one‑line DDL change when the dataset grows.

### Naming convention

The vector table is named `{item_table}_name_vecs` (e.g. `items_name_vecs`).
This keeps related tables grouped lexically in `\dt` listings.
