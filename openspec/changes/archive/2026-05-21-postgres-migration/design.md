## Context

The current OParl ingestion pipeline (`references/postgres/dbGen.py`) creates a MariaDB schema, stores the raw JSON payload, and builds a series of tables and association tables based on detected relationships. PostgreSQL is required for two reasons:
1. **Vector support** – the `pgvector` extension (and related tooling) is available only on PostgreSQL, enabling efficient similarity search for embedding vectors.
2. **JSONB indexing** – PostgreSQL’s `jsonb` type offers powerful indexing (GIN) and query capabilities that are more performant for deep OParl queries.

The migration must be non‑destructive: any existing PostgreSQL database (including custom vector tables) should be left untouched. The script must therefore:
- Detect whether each OParl table already exists and create it only if missing.
- Detect rows that already exist (by `oparlId`) and **update** them when the source JSON reports a newer `modified` timestamp (or when the row is missing).
- Preserve any additional tables (e.g., `entity_vectors`) that are not part of the OParl schema.

## Goals / Non-Goals

**Goals:**
- Produce a drop‑in replacement `src/dbPgGen.py` that runs against PostgreSQL.
- Use `psycopg2` as the driver via SQLAlchemy.
- Preserve existing vector tables and data – the script never drops tables it does not own.
- Implement an upsert‑style insert: new rows are inserted, existing rows are updated only when the OParl object’s `modified` field is newer.

**Non-Goals:**
- Migrate data from the existing MariaDB instance; this change assumes the JSON files are the source of truth.
- Refactor the overall OParl data model – we keep the same table layout generated by the original script.

## Decisions

1. **Engine URL** – Use `postgresql+psycopg2://{user}:{pwd}@localhost/{db}`. `psycopg2-binary` will be added to `requirements.txt`.
2. **JSON column** – Switch from MySQL `JSON` to PostgreSQL `JSONB` (`from sqlalchemy.dialects.postgresql import JSONB as PGJSON`). This provides indexing and faster containment queries.
3. **Upsert strategy** – Replace MySQL `INSERT … IGNORE` with PostgreSQL `ON CONFLICT (oparlId) DO UPDATE SET ... WHERE excluded.modified > table.modified`. SQLAlchemy’s `insert().on_conflict_do_update()` will be used.
4. **Schema creation** – Call `metadata.create_all(engine)` which issues `CREATE TABLE IF NOT EXISTS`. Existing tables (including custom vector tables) remain untouched.
5. **Column quoting** – Preserve the `quote` flag for reserved words (`order`, `group`, …) because PostgreSQL also treats them as identifiers.

## Risks / Trade-offs

- **Risk:** Existing PostgreSQL tables may have differing column definitions (e.g., `jsonb` vs `json`). *Mitigation*: Use `CREATE TABLE IF NOT EXISTS` and only add missing columns via `ALTER TABLE … ADD COLUMN IF NOT EXISTS` (SQLAlchemy does not emit `ADD COLUMN IF NOT EXISTS` automatically; we will add a lightweight post‑creation step that checks column existence and adds missing scalar columns).
- **Risk:** Upsert `ON CONFLICT` may overwrite rows unintentionally if the `modified` field is missing or malformed. *Mitigation*: Treat missing `modified` as the oldest possible timestamp; only update when the source timestamp parses successfully and is newer.
- **Risk:** Compatibility with older PostgreSQL versions (<9.5) which lack `ON CONFLICT`. *Mitigation*: The project targets PostgreSQL 12+ (required for `pgvector`).

## Migration Plan

1. **Add dependency** – `psycopg2-binary` to `requirements.txt`.
2. **Create `src/dbPgGen.py`** – copy `dbGen.py`, apply the code changes listed above.
3. **Test against a fresh PostgreSQL database** – ensure tables are created, data is inserted, and updates respect the `modified` timestamp.
4. **Run against a database that already contains custom vector tables** – verify they remain untouched.
5. **Document usage** – update README to point to `dbPgGen.py` for PostgreSQL.

## Open Questions

- Will we need to add GIN indexes on the `data` column for frequent OParl queries? (Can be added in a later optimisation step.)
